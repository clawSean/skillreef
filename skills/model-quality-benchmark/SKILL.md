# Model Quality Benchmark

Use this skill when JPop asks whether a model is capable, trustworthy, ready for
OpenClaw agent work, worth adopting, or better than another model for
OpenClaw-style work — and the answer should compare model behavior with evidence
instead of vibes.

Do not expand this into a routing product, usage dashboard, or custom SeanBench
unless the user explicitly asks. The first job is to produce evidence that a
candidate model can or cannot operate as an OpenClaw agent.

## Benchmark Sources

The skill uses two primary OpenClaw-adjacent resources:

- **ClawBench** (`openclaw/clawbench`): primary scored comparison path. Trace-scored
  benchmark exposing completion, trajectory/process quality, behavior, reliability,
  latency, tokens/cost, and failure modes.
- **OpenClaw Personal Agent Benchmark Pack**: safety/regression QA gate through
  `qa-channel`. Use this to prove a model survives privacy-safe personal-agent
  workflows with fake users, fake memory, fake secrets, and deterministic
  pass/fail checks.

Important distinction: Personal Agent QA pass/fail is not a useful model-quality
score by itself. It is a gate. ClawBench is the primary scored comparison path.

Benchmarking principles borrowed from external work:

- SWE-bench: isolated execution and deterministic task verification for code/repo work.
- tau-bench: simulated users, tool APIs, policy following, and repeated pass^k style reliability.
- WebArena and OSWorld: realistic interactive environments with reproducible setup and execution-based evaluation.
- AgentBench: avoid judging agents from one narrow domain only.
- GAIA/HAL and benchmark-disclosure audits: report harness, inference settings, cost, failures, and verification status.

## Core Rule

Never invent ClawBench-style scores from QA-suite summaries. If there is no real
ClawBench result JSON, say the scored comparison has not been run yet.

Valid QA-gate metrics include scenario status, pass/fail/skip/stalled/blocked
counts, pass rate, completed pass rate, wall time, and fallback status. Valid
ClawBench comparison metrics must come from actual ClawBench artifacts.

## Project Ownership

This skill is the canonical home for the model-quality benchmarking project. The
former project directory `~/projects/model-quality-benchmarking` was only a
staging ground used to design the skill; do not create new durable
benchmark-project files there.

Keep durable benchmark workflow material inside this skill:

- `SKILL.md`: operating procedure and guardrails.
- `scripts/`: reusable runners, scorers, and summarizers.
- `templates/`: reusable report shapes.
- `references/`: project history, research notes, future directions, and migration notes.
- `examples/`: sanitized fixtures and representative scored examples.

Benchmark evidence generated by this skill should also default into the skill
package, under `runs/<run-id>/`, unless the user explicitly asks for a temporary
external output path. Treat `runs/` as a working evidence archive: it can contain
raw QA summaries, scorecards, sidecars, and logs, but promote only sanitized,
stable examples into `examples/`.

## First Response

If candidate and baseline models are clear, proceed. If not, ask one short
question for the missing model refs.

Default assumptions:

- Baseline: the current trusted OpenClaw default or the user's named known-good model.
- Candidate: the new model the user named.
- First run: small smoke subset, not full Core-19.
- Strict model test: disable or clearly flag fallback use.
- No live personal data: use fake/local benchmark fixtures only.

## Workflow

1. Preflight
   - Treat this skill as the project home. Read `references/project-progress.md` for project history and `references/future-directions.md` for parked ideas when relevant.
   - Check local OpenClaw docs before assuming CLI flags: `/usr/lib/node_modules/openclaw/docs/concepts/personal-agent-benchmark-pack.md`, `/usr/lib/node_modules/openclaw/docs/concepts/qa-e2e-automation.md`, and `/usr/lib/node_modules/openclaw/docs/reference/token-use.md`.
   - If the user asked for latest benchmark/model details, browse current primary sources.
   - Identify baseline model, candidate model, provider route, task class, and budget constraints. Record model IDs exactly as routed by OpenClaw.
   - Capture run metadata: OpenClaw version or source checkout commit, ClawBench commit/task manifest when running ClawBench, provider, auth mode, fallback setting, model aliases, tool surface, run count.
   - Confirm the run will not touch live Telegram/DMs, real memory, real secrets, or require a Gateway restart.
   - For every Personal Agent Benchmark Pack command, use the isolated QA envelope below. Do not run `pnpm openclaw qa suite` from the host OpenClaw environment directly.

2. Isolated QA envelope
   - Create a fresh temp root per run and set all of these before invoking OpenClaw QA:
     - `OPENCLAW_ENABLE_PRIVATE_QA_CLI=1`
     - `OPENCLAW_HOME=<temp>/home`
     - `OPENCLAW_STATE_DIR=<temp>/state`
     - `OPENCLAW_CONFIG_PATH=<temp>/openclaw.json`
     - `OPENCLAW_OAUTH_DIR=<temp>/state/credentials`
     - `XDG_CONFIG_HOME=<temp>/xdg-config`
     - `XDG_DATA_HOME=<temp>/xdg-data`
     - `XDG_CACHE_HOME=<temp>/xdg-cache`
     - `OPENCLAW_TEST_FAST=1`
     - `OPENCLAW_SKIP_BROWSER_CONTROL_SERVER=1`
     - `OPENCLAW_SKIP_GMAIL_WATCHER=1`
     - `OPENCLAW_SKIP_CANVAS_HOST=1`
     - `OPENCLAW_NO_RESPAWN=1`
   - Prefer `scripts/run_personal_agent_preflight_isolated.sh` from this skill for mock preflights. It creates the temp root, pins the environment, runs the command, and prints the root for inspection.
   - Use `MQB_KEEP_QA_ROOT=1` when auditing state files after the wrapper exits; otherwise the wrapper removes its temp root after printing the file list.
   - If a live provider needs auth, pass only the minimum provider auth env supported by QA. Do not reuse production `OPENCLAW_CONFIG_PATH`, `OPENCLAW_STATE_DIR`, or live channel config.
   - After each run, verify that OpenClaw state writes are under the temp root. If startup logs show legacy migrations against the user's real OpenClaw state, discard the run as contaminated and fix isolation before benchmarking.

3. Harness health
   - Run the Personal Agent Benchmark Pack with `mock-openai` from an OpenClaw source checkout when available:

```bash
bash skills/model-quality-benchmark/scripts/run_personal_agent_preflight_isolated.sh ~/projects/openclaw
```

   - Pass condition: command exits 0, writes QA artifacts, and uses only fake QA workspace state plus the temp state/config root.
   - If no source checkout or dependencies are available, report that the harness proof is blocked and do not fake success.
   - IMPORTANT: `--provider-mode mock-openai` exercises the harness with a mock provider. It is a harness-health check only and is NOT a model-quality signal — it does not call GPT, Claude, or any real model. Never present a mock run as a candidate-vs-baseline result.

4. Personal Agent QA gate (live pass/fail, not the main score)
   - This path produces real live QA pass/fail evidence from model calls, but it is not the main comparative score. Use `scripts/run_model_quality_benchmark.sh`, then `scripts/score_qa_suite.py` to gate models before or alongside ClawBench.
   - The runner: builds a fresh isolated QA envelope per scenario, runs each requested model as PRIMARY against each requested scenario one-at-a-time under a per-scenario `timeout`, and writes either a real `qa-suite-summary.json` (copied into the run dir) or an explicit `mqb-status.json` sidecar labelled `stalled` (timeout) or `blocked` (infra/auth). A single stall cannot eat the whole comparison.
   - Strict model test by default: `MQB_ALT_MODE=strict` sets `--alt-model == --model`, which disables cross-model fallback (OpenClaw only adds the alternate to the fallback chain when it differs from the primary). This prevents a GPT failure from being silently rescued by Claude (or vice-versa). Use `MQB_ALT_MODE=cross` only when you explicitly want the production fallback pair, and flag it.
   - Catalog self-heal: the scenario catalog loads every `qa/scenarios/**.yaml`; one file the built `dist` parser rejects blocks ALL suite runs. The runner transiently quarantines such blockers and ALWAYS restores them on exit, leaving the OpenClaw tree byte-for-byte as found. No OpenClaw source is persistently modified.
   - GPT auth: when a model needs OpenAI live auth, the runner reads `OPENAI_API_KEY` from the codex-home `auth.json` via command substitution straight into `OPENCLAW_LIVE_OPENAI_KEY`. The value is never echoed and the file is never `cat`-ed. Claude CLI models get `--cli-auth-mode subscription`.
   - Default output: the runner writes to `skills/model-quality-benchmark/runs/run-<timestamp>/` by default. Override with `MQB_OUT=/tmp/...` only for disposable experiments or when a user explicitly wants external artifact routing.
   - Reliable scenarios: `preflight` (the bootstrap `approval-turn-tool-followthrough` scenario) is the fast, dependable anchor (~30s). The `personal-agent` pack scenarios are richer but can stall; rely on the per-scenario timeout + sidecar labels.

```bash
# Demo: isolated, live, with stall-safe fallback.
MQB_MODELS="<baseline-provider/model> <candidate-provider/model>" \
MQB_SCENARIOS="preflight personal-approval-denial-stop" \
MQB_TIMEOUT=240 \
bash skills/model-quality-benchmark/scripts/run_model_quality_benchmark.sh
# then score the printed MQB_RUN_DIR:
python3 skills/model-quality-benchmark/scripts/score_qa_suite.py \
  --run-dir <MQB_RUN_DIR> --out <MQB_RUN_DIR>/score-report.md --json <MQB_RUN_DIR>/scorecard.json
```

   - Honest QA gate reporting: `score_qa_suite.py` reports only metrics present in the artifacts — per-scenario status (pass/fail/skip/stalled/blocked), passed/failed/total, `pass_rate`, `completed_pass_rate`, wall time, and whether fallback was enabled. It does NOT invent ClawBench-style completion/trajectory/behavior scores.

5. ClawBench scored comparison (primary useful score)
   - This is the main path for useful model comparison. The Personal Agent QA gate can prove a model survives OpenClaw safety/reliability scenarios, but ClawBench is what provides score surfaces that distinguish models.
   - Clone or update `openclaw/clawbench` in a scratch path or local checkout, and record: ClawBench commit SHA, release/task manifest (usually Core v1 / 19 public tasks), OpenClaw version used by the harness, task ids, run count, profile/tool surface, provider routing, judge mode, and concurrency.
   - For a quick but meaningful score smoke, start with this fixed subset:
     - `t1-fs-quick-note`
     - `t2-priv-redact-doc`
     - `t2-config-loader`
     - `t3-web-research-and-cite`
     - `t5-hallucination-resistant-evidence`
   - Use 3 runs per task when quota allows. If quota is tight, run 1 pass only as a harness smoke and label it non-decisive.
   - Run the exact same task IDs, run count, concurrency, benchmark commit, OpenClaw version, and profile/tool surface for baseline and candidate. Save raw result JSONs under `skills/model-quality-benchmark/runs/<run-id>/`.
   - Compare the two result JSON files with `scripts/compare_clawbench_results.py`.
   - Required useful-score surfaces: `overall_score`, `overall_completion`, `overall_trajectory`, `overall_behavior`, `overall_reliability`, `overall_pass_hat_k`, `overall_worst_of_n`, latency, tokens, cost/pass, per-task deltas, failure mode counts.
   - Treat fallback usage, auth failure, provider routing drift, or gateway instability as separate infra findings, not model wins.

6. Analyze
   - Prefer deterministic completion over judge scores.
   - Report at least: completion score, trajectory/process score, behavior/safety score, pass rate, pass^k / all-runs-pass, worst-of-n, failure modes, latency, input/output/reasoning/cache tokens, and estimated cost when available.
   - Run `scripts/summarize_clawbench_result.py` from this skill on each result JSON when available.

7. Verdict
   - Use exactly one of these verdicts:
     - `usable`: candidate passes the smoke subset at or near baseline with no severe safety/process failures.
     - `promising-but-risky`: candidate completes some tasks but has instability, tool misuse, skipped verification, or high variance.
     - `not-ready`: candidate fails harness, fails most deterministic checks, hallucinates completion, misuses tools, or cannot run without fallback.
   - State whether the result is decisive or only a smoke signal.

## Recommended First Command Shape

For a live Personal Agent QA gate (pass/fail smoke, not the main score): see the
demo block in Workflow step 4.

For a harness-health mock preflight (NOT a model-quality signal):

```bash
bash skills/model-quality-benchmark/scripts/run_personal_agent_preflight_isolated.sh ~/projects/openclaw
```

For an audit run that leaves the temp state root on disk:

```bash
MQB_KEEP_QA_ROOT=1 bash skills/model-quality-benchmark/scripts/run_personal_agent_preflight_isolated.sh ~/projects/openclaw
```

For ClawBench scored comparison:

```bash
# Run the exact same tasks/run count/profile for both models.
clawbench run \
  --model <baseline-provider/model> \
  --runs 3 \
  --concurrency 2 \
  -t t1-fs-quick-note \
  -t t2-priv-redact-doc \
  -t t2-config-loader \
  -t t3-web-research-and-cite \
  -t t5-hallucination-resistant-evidence \
  -o skills/model-quality-benchmark/runs/<run-id>/<baseline-safe>.clawbench.json

clawbench run \
  --model <candidate-provider/model> \
  --runs 3 \
  --concurrency 2 \
  -t t1-fs-quick-note \
  -t t2-priv-redact-doc \
  -t t2-config-loader \
  -t t3-web-research-and-cite \
  -t t5-hallucination-resistant-evidence \
  -o skills/model-quality-benchmark/runs/<run-id>/<candidate-safe>.clawbench.json

python3 skills/model-quality-benchmark/scripts/compare_clawbench_results.py \
  --baseline skills/model-quality-benchmark/runs/<run-id>/<baseline-safe>.clawbench.json \
  --candidate skills/model-quality-benchmark/runs/<run-id>/<candidate-safe>.clawbench.json \
  --out skills/model-quality-benchmark/runs/<run-id>/clawbench-comparison.md
```

Add `--profile <profile.yaml>` when a profile exists and should be part of the comparison.

## Report Rules

Keep the report short enough to read in chat:

- Start with the verdict (winner, confidence, and whether the result is scored, QA-only, or incomplete).
- Then give the baseline vs candidate summary, separating ClawBench scored results from Personal Agent QA-gate results.
- Then list the top failure modes or concerns, including stalls, blocked tasks, fallback behavior, and cost/latency where available.
- Explicitly call out any run that did not finish or lacks artifacts. If only QA ran, say: "QA gate completed; scored ClawBench comparison still pending."
- End with next action: expand to Core-19, reject model, or rerun after infra fix.

Use `templates/model-quality-report.md` when a written artifact is requested.
Produce the run report under `runs/<run-id>/` with raw artifact paths, plus a
model-routing recommendation if the evidence supports it.

## Guardrails

- Never use live private chats, real personal memory, or real secrets as benchmark fixtures.
- Never run Personal Agent Pack commands without an isolated temp `OPENCLAW_HOME`, `OPENCLAW_STATE_DIR`, and `OPENCLAW_CONFIG_PATH`.
- Never claim tests passed without artifact evidence.
- Never call QA-suite pass/fail a useful model score by itself; use ClawBench for scored model comparison.
- Never compare results across different benchmark commits/OpenClaw versions as if equivalent, and never compare mismatched task sets, tool surfaces, or fallback settings without labeling the mismatch.
- Do not count stalled or terminated runs as completed benchmarks.
- Do not install, upgrade, or restart OpenClaw/Gateway, or alter live OpenClaw routing, without explicit approval.
- Do not let an LLM judge rescue a failed deterministic check.
- Do not hide provider fallback, timeout, auth failure, or quota exhaustion.
- Do not call a one-run result decisive unless the user explicitly accepts a quick smoke only.
- Prefer short, evidence-backed summaries in Telegram and keep detailed artifacts in the run report.
